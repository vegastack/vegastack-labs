**Scope:** full-plan — the second child of the approved #115 split owns one independently rejectable destructive mechanism: exact off-site lock-rule subtraction and sealed-generation object retirement with external one-owner and survivor proof.
**Development ID:** [5.5.4] — proposed title: `feat: [5.5.4] Retire exact off-site recovery generations safely`. #117 already owns [5.5.3].

## Outcome

An infrastructure administrator can inspect an eligible sealed generation from #115's deterministic selection, approve a recovery-prechecked exact retirement plan naming its one point, five owned lock rules and complete object-key/byte inventory, and execute off-site retirement through separate lock-admin and retention identities. The adapter subtracts only those five rules via Cloudflare's full-rule-configuration PUT under a qualified exclusive one-owner administration period, then rereads all rules; only after exact rule and object inventory agreement may it delete listed generation objects. Every surviving off-site last-good point gets full-read and isolated-restore proof. Any rule/provider race, response loss or partial delete remains append-only uncertain and blocks further deletion/restore admission rather than shrinking the recovery promise.

## Out of scope

- Creating local points or off-site generations (#106/#114), local restic `forget`/`prune` (#115), schedule/timer policy, controller cutover, emergency generic bucket cleanup, live R2 rule/token/bucket modification during development, or inventory-fleet operation.
- A routine writer/scheduler with rule/delete authority; broad bucket-wide/unlisted object deletion; an invented bucket-lock compare-and-swap or proof that a fake one-owner fixture qualifies live G-008.

## Phase position and dependencies

- Wave C after merged #114 exact off-site generation/rule/object catalog and expiry seal, merged #117 qualified local full-read/functional-restore proof, merged local-only #115 selection/intent/receipt contract, #105 separate JIT lock-admin/retention identities, current #104 gate proof for live admission and Phase 4 exact human plan/run. Do not implement against unmerged generation/retirement/proof seams; use the next sequential unapplied migration ID from freshly merged main if persistence needs one.
- #108 restore and #109 schedules treat uncertain off-site retirement, missing rule/object/survivor proof or unqualified G-008 as recovery blockers. This development issue does not claim actual R2 race/denial/key/capacity/live recovery qualification.

## Rules and edge cases

- Standard local remains 7 days, critical local 14 days and critical off-site 14 days, all relative to the latest verified point. The sole surviving last-good generation is retained despite backup outage. An unverified point, active rollback/recovery promise, stale source/manifest/epoch, ambiguous inventory/dependencies or changed policy blocks selection/admission; age alone never schedules deletion.
- Every sealed off-site generation contains exactly one protected point; never run restic `forget`/`prune` inside it. An exact dry-run lists target generation/point ID, full rule IDs/prefixes, complete pre-rule-set digest/count, unchanged survivor-rule digest, object keys/bytes and expected retained/reclaimed bytes, survivor IDs/dependencies, current recovery epoch, plan/revision/source/manifest/catalog/inventory digests and max work. Infrastructure-admin human acknowledgement plus verified recovery precheck and a current Phase 4 exact plan are mandatory for rule removal and object DELETE; no agent/scheduler/routine writer self-approval.
- Cloudflare's bucket-lock management API uses PUT of the **entire** lock-rule configuration to remove rules; no documented `If-Match`/ETag CAS is assumed. The exact plan subtracts only the five owned generation rules. A qualified exclusive one-owner lock-rule-administration period for the bucket, with separately scoped admin identity and actual G-008 provider evidence, is required before live PUT. Full pre-read/digest/count must match the plan, then PUT only planned subtraction, then full post-read proves all survivor rules unchanged and target rules absent. An out-of-band external admin can still race between read and PUT; post-read cannot undo overwritten rules. Missing qualification, rule drift, external-admin race or lost PUT response is uncertain and forbids every object DELETE.
- Check strictest overlapping lock rules and lifecycle behavior, session-expiry seal and the 1,000-rule ceiling; fake fixtures only prove adapter logic. A separate retention identity may delete only **listed** target generation keys after qualified rule receipt and exact object inventory recheck. Each DELETE response/key is appended; a partial delete or response loss stays uncertain. Retry lists only still-present exact keys under a fresh current human plan; no prefix sweep or broadened permission.
- After effects, compare complete rule and object-key/byte inventories, ensure every survivor generation's rules/objects remain intact, run full `check --read-data` and exact-point isolated restore for every surviving off-site last-good, and measure reclaimed bytes. Only this proof settles an append-only verified receipt; no direct status edit/DELETE route or deletion-only last-good advance. G-008 is still live evidence, not a fixture result.
- Capacity/retention forecast accounts for encrypted retained bytes, expected growth, 30% headroom and off-site rule-count ceiling; warn at 70% current utilization and block new standard targets at 80%. Critical work only if projected bytes fit with headroom, otherwise fail closed/alert instead of deleting the only good generation or shortening 14 days.
- Manual fallback uses the same exact point/rules/object list, one-owner/admin qualification, distinct identities, human plan/recovery precheck, pre/post inventories, survivor full-read/isolated restore and response-loss/retry rules. A manual provider CLI is not used for convenience; break-glass retains separate authority and later database revision.

## Risks and stop conditions

- Stop if a sole survivor is unverified, rule/object inventory differs from the plan, a one-owner period cannot be qualified, a routine writer can delete, an external-admin race can overwrite survivor rules without being detected, or post-effect full restore fails.
- Stop if provider API/real behavior cannot support bounded full-rule PUT and exact listed-key DELETE; do not invent CAS, widen deletion, shorten retention or treat response loss as success.
- Stop before destructive live R2 PUT/DELETE, new credential/grant, provider/host/fleet action, release or deployment without separate authority. Fake one-owner/race fixtures never qualify G-008.

## Plan (v1)

**Goal:** An infrastructure administrator can plan one exact off-site generation retirement, remove only its five owned R2 lock rules under qualified one-owner administration, delete only its inventoried objects through a separate identity, and settle an append-only verified receipt only after all survivors pass full-read and isolated restore.
**Approach:** Add a distinct `backup.retire.offsite` exact human-branch effect consuming #115's selection/intent, #114's immutable generation/rule/object catalog and #117's qualified point proofs. Use the existing typed Cloudflare/R2 adapter boundary with full rule-set read → exact subtraction PUT → full reread, then a separate listed-key object deletion boundary and post-effect survivor verifier. Rejected alternatives are per-rule deletion or an invented ETag compare-and-swap (Cloudflare's documented API removes rules by full configuration PUT and does not establish that CAS), and allowing a routine writer or timer to delete (which collapses retention separation). [Cloudflare's bucket-lock documentation](https://developers.cloudflare.com/r2/buckets/bucket-locks/) confirms full-configuration PUT for removal, strictest overlapping rule precedence and the 1,000-rule ceiling; current API behavior must be rechecked before live qualification.
**Constraints:** Claim only after merged and verified #114 generation catalog/expiry seal, #115 local-only selection and inert intent/receipt contract, #117 local full-read/isolated restore, and #105's exact JIT consumer seam. Re-ground all symbols/migration IDs on current merged `main`; this plan grants no live provider or destructive authority.
**Constraints:** An off-site generation has exactly one protected critical point. Select `keep-within 14d` relative to the newest verified point; preserve sole last-good, active recovery/rollback promises, dependencies and 30% headroom. Warn at 70%, block new standard at 80%, and deny critical work that cannot fit. No age-only or scheduled deletion.
**Constraints:** An exact dry-run binds one generation/point, five owned rule IDs/prefixes, full pre-rule-set digest/count and survivor-rule digest, every object key/byte/digest, expected retained/reclaimed bytes, survivor IDs/dependencies, source/manifest/catalog/inventory digests, plan/revision/epoch/max work. Changed material or missing external one-owner qualification denies the effect.
**Constraints:** Rule administration uses a distinct `lock-admin` JIT identity; object deletion uses a distinct `retention` JIT identity. Neither routine writer nor scheduler can obtain either. Infrastructure-admin human acknowledgement, verified recovery precheck, current exact Phase 4 plan and active step lease are required for every destructive attempt.
**Constraints:** A full-configuration PUT cannot be treated as atomic compare-and-swap. An external administrator can race between pre-read and PUT, and post-read cannot undo a clobbered survivor. Missing qualified exclusive one-owner period, drift, lost response or ambiguous race is `uncertain`; no object DELETE follows. Actual one-owner/provider qualification and G-008 are external live gates, never inferred from fake R2 tests.
**Constraints:** Rule removal precedes any object DELETE. After a qualified rule receipt, recheck complete listed-key inventory and strictest overlapping/lifecycle retention; delete only listed target keys. Each attempt/result is append-only. Retry only still-present exact keys under a new human plan; no prefix sweep, `forget`/`prune`, direct DELETE/status-edit route or status promotion from deletion alone.
**Constraints:** Every surviving off-site last-good retains exact rules/objects and passes full `check --read-data` plus exact-point isolated restore. Failure or uncertainty preserves earlier last-good and blocks affected restore/admission. No live R2 PUT/DELETE, provider/credential/host/fleet operation, release or deployment occurs in development tests.
