# Hosting and registry lifecycle

Use `vsk-labs hosting lifecycle draft --config <protected-client-profile> --file <private-request.json> --output json` to prepare one configured hosting target. Read its last result with `vsk-labs hosting lifecycle show --config <protected-client-profile> --target-id <target> --output json`. Preparation performs authorized reads and creates an inert declaration. Use the existing declaration commit, exact plan, human acknowledgement and apply workflow before any provider write.

The server profile's `hostingLifecycleProfiles` selects a binding/target, protected configuration file and its SHA-256, Coolify mutation reference and native platform reference. Public requests select the target and `resources.apply`; they cannot submit provider URLs, Compose, credentials, machine addresses or commands. The request also carries the current state revision/recovery epoch, idempotency key and reason digest. Changed protected bytes, current grants/devices, epoch, physical identity, provider scope, role admission or credential material block the operation.

The protected configuration enumerates the complete `targets` set: controller, selected application destination and registry machines, each with `hostId`, `identityDigest` and `role` (`control` or `application`). The server requires current role admission and follows physical exclusions through alias/history records before a provider connection. Nodes04/05 remain excluded. A configuration record is not admission evidence.

A `coolify` binding contains its origin, controller `hostId`, `destinationHostId`, and typed `resources`: team ID, project name/optional existing project UUID, environment name, explicit server ID/UUID/address and destination UUID; optionally an existing application/service UUID or a new application name and image/tag/ports or protected Compose content. Creation uses the selected v4.3.10 routes with `instant_deploy=false`; this workflow creates provider configuration, not a running application. The service deployment workflow separately authorizes signed-image deployment and verifies runtime health/digest. An existing team and its token are an administrator prerequisite because the pinned API has no team-creation route. Name collisions are never silently adopted. Existing external resources require their explicit protected identity.

A `harbor` binding contains its origin, `hostId`, administrator username, separate management reference and typed `resources`. Projects enumerate their explicit IDs/names/public flags, retention IDs and keep-last counts. Two expiring SYSTEM robots are required: one CI push/pull and one deployment pull-only, each with an exact `robot$...` name, reference ID/material version, duration and complete project namespace set. The selected profile intentionally accepts the existing cross-project blast radius; it does not create per-project robots or widen their namespace set.

Create robot credential material through the existing protected import/activation workflow first. Provider creation borrows that exact active reference and supplies its already protected secret to Harbor's documented `RobotCreate.secret`; a returned secret must match. No new plaintext file or credential output is produced. Generated one-time-secret handling is not an alternative public workflow. The management credential is separate from both robot identities. Reference consumers/capabilities are `registry.harbor.manage` / `credential.registry.manage`, `registry.harbor.ci` / `credential.registry.push`, and `registry.harbor.deploy` / `credential.registry.pull`. Purposes are respectively `registry-manage`, `registry-push` and `registry-pull`; each reference targets the exact hosting target. Coolify uses `hosting.coolify.deploy` / `hosting-deploy` / `credential.hosting.deploy`.

Retention configuration uses a manual policy and preserves `vsk-recovery-**` tags. This operation does not execute retention or garbage collection. It cannot establish that every retained deployment/backup digest has a protective tag; a deletion operation still requires its actual protected artifact inventory and recovery prerequisites. Repositories materialize through image publication; no empty-repository creation endpoint is invented. Robot permission/expiry checks verify actual provider configuration; they do not replace live credential positive/negative qualification.

The SQLite journal records an attempt before provider I/O. A transport failure can leave actual external changes even if no identifier was returned. An attempted plan cannot repeat its mutation, including after a server restart. Partial/unknown results require a fresh bounded reconciliation/recovery plan; there is no automatic project deletion, volume removal or host rebuild. Independently observed external IDs are retained as owned resources. Provider configuration success does not mean workload installation, host admission, signed artifact verification or data recovery passed.

## Selected Coolify platform installation

Use the existing `vsk-labs host action draft` workflow for `hosting.platform.install` or `hosting.platform.verify`, action version `1.0.0`. These actions travel through the existing signed exact-plan/SSH/native dispatcher. They do not run inside the hosting HTTP lifecycle effect. The host-action request must match one protected hosting profile's `platform` input, native reference, physical identity and complete admitted target set.

Stage the reviewed local component files on an independently initialized qualified control machine before planning: `/data/coolify/compose.yaml` and `/data/coolify/environment`. Docker and all selected digest-pinned images must already be present. The selected deployment composes the official v4.3.10 base/production definitions, with explicit private port binds and persistent bind mounts beneath `/data/coolify` to make the declared backup dataset complete. It contains exactly `coolify`, `postgres`, `redis`, and `soketi`; every image is immutable and the Coolify image is `docker.io/coollabsio/coolify:4.3.10@sha256:<digest>` (the Docker Hub shorthand is also accepted). Stage each file as a protected root-owned regular file; no symlink or writable parent is accepted. Keep secret-bearing environment content in the existing protected channel, never a public plan or repository.

The finite native input binds `hostId`, `hostIdentityDigest`, `componentDirectory` (`/data/coolify`), `composeDigest`, `environmentDigest`, private/loopback `privateAddress`, `managementPort`, `controllerDatabasePath`, and the current `controllerUnitDigest`. The environment and rendered Coolify environment must disable automatic updates. The action rejects builds, privileged/host namespaces, extra capabilities/devices and binds outside the component dataset. It invokes fixed Docker Compose configuration and `up --detach --wait --wait-timeout 40 --no-build --pull never`, then independently reads all four running/healthy component records and their selected immutable images. Its bounded wait can return partial if startup has not converged; it never treats the command exit alone as platform verification.

Before and after an installation attempt, the action checks the unchanged controller unit digest, same database file identity and active independent `vsk-labs.service`. Failure preserves the component files, volumes and controller. Diagnosis and a separately approved recovery use their actual state; no automatic cleanup removes data. The vendor install shell is not invoked: its selected public script downloads mutable CDN content and may alter Docker. No installer download, package installation, arbitrary shell, new daemon or second signing authority is introduced.

This proves selected local component state and private binding. HTTPS management-origin, browser/private access, actual token permissions and independent machine qualification still require their operation-specific evidence. A private bind is not a claim that a TLS gateway or remote access policy is qualified.

## Backup, restore and migration

Coolify's database/configuration and workload/Harbor volumes are separate datasets. Use the approved workload recovery workflow with the correct declared `platform`, `registry` or `workload` class, exact persistent volume/container inventory, encrypted backup and isolated restore target. A SQLite control backup cannot recover Coolify or Harbor data. Harbor recovery must reconcile component state, catalog/digests and credential behavior before cutover. Migration preserves the source and uses a separate exact cutover plan; no route is changed by a resource-creation result.

For the human fallback, perform the same protected-profile, full-target/admission, current credentials, recovery and exact-plan checks; inspect readable and JSON plans; obtain the same human acknowledgement; execute the existing CLI and inspect independently observed results. If the supported operation is unavailable, stop and preserve the attempt. Emergency app-owner actions require their existing scoped authority, audit and reconciliation; direct provider consoles do not become an untracked alternate owner.

Public TLS/process/SQLite fixtures demonstrate software behavior only. No live installation, admission, registry migration or Phase 8 deployment gate is closed by these tests.
