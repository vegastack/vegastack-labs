## Product, profile and support

`vsk-labs` is the OSS product; VegaStack Labs is one deployment using it. Product setup selects a supported control host, never a hard-coded node number. The Labs profile binds that role to `vsk-node-04`; its hardware, domain, accounts, topology, capacity and policies do not become core prerequisites. Preserve the four existing layers: core, typed adapter, optional capability and deployment profile. An installed adapter does not enable a feature, and selecting a profile grants no authority.

Account-free local and constrained-SSH access must support read-only inspection, inert draft/plan preparation, local credential management and documented recovery for supported reachable nodes. It does not authorize normal v1 bootstrap or mutation: those paths require the selected Slack acknowledgement adapter, an approved workspace/user mapping and Slack network availability. This accepted v1 limitation does not make Slack an operational-state, audit or execution authority, and it does not make Cloudflare, Workspace, 1Password, GitHub, Labs naming or physical inventory core prerequisites. Provider-dependent operations explicitly name their required capability and supported adapter. [D-122](decisions-and-sources.md#d-122)

Keep the [existing support matrix](automation-and-agents.md#os-and-architecture-support-matrix). A single supported control host with zero managed nodes is a valid initial installation. Arbitrary control/application/CI colocation, unsupported OS/architecture combinations, multiple active controllers, automatic HA and a multi-tenant hosted control service are not implied. Hardware/virtualization kinds require tested profile support; a provider-neutral identity schema alone does not qualify a new environment.

No general command shell is exposed, and SSH identity cannot acknowledge a mutation. |

The v1 Slack acknowledgement adapter runs inside `vsk-labs server run` over Socket Mode; it is not a public webhook, second daemon or controller. Its minimum declared Slack permissions are the app-level `connections:write` scope for opening Socket Mode connections and the bot `chat:write` scope for presenting approval requests. Tokens and signing material appear only as logical secret references and are resolved by the owning secret-delivery path. Core records remain provider-neutral: an approval request/proof interface binds the exact subject digest, target-set and reason digests, risk, responsible local human, expiry, nonce, state revision and recovery epoch; Slack workspace/user/action/envelope fields live in the typed adapter/profile boundary. [Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/) · [`connections:write`](https://docs.slack.dev/reference/scopes/connections.write/) · [`chat:write`](https://api.slack.com/scopes/chat%3Awrite)

The base local credential resolver is an OS-profile implementation, not a new general secrets manager. On the supported Debian control profile, qualify native systemd encrypted service credentials for persistent host-bound material and restrictive runtime delivery to the service. Persist only opaque references in SQLite; import/generate/rotate via an approved plan and protected input, never CLI secret arguments or printed output. Pin the actual supported systemd behavior in the implementing issue. Host-key encryption protects access but does not claim resistance to root or whole-disk theft when the host key is on the same disk. Do not silently require TPM hardware. Independent encrypted recovery must include what is needed to recover/re-encrypt onto a new host without copying its old execution authority; prove this before node-loss readiness. If qualification fails, the affected implementation issue must return a concrete local resolver design, not silently require 1Password. [systemd credential contract](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd-creds.xml)

The native credential lifecycle is implemented through the shared API, plan and run engine. A protected local import creates inert host-key ciphertext; exact human-approved `credential.stage`, `credential.activate`, `credential.rotate`, `credential.revoke` and `credential.recover` plans append immutable status and evidence records. Native activation and rotation require the sealed systemd consumer map, real process restart, positive loaded-credential observations and every required denied-reader result. Rotation keeps the prior version active during the bounded overlap and requires a separate named revoke. Recovery requires the current replacement epoch, the independently signed custody/fence package, its one-use handoff receipt and exact opened-ciphertext comparison. The optional 1Password resolver remains unregistered, so its absence cannot disable this local core or imply provider support.

This is software completion, not live authority. The production live-evidence gate and production recovery-source registry remain unavailable until the site enrolls and qualifies their exact adapters and evidence; current replacement authority is established separately by the restore procedure. A successful disposable acceptance run cannot close `G-007`, enroll a provider, create a live grant or authorize deployment. Existing local inspection and backup primitives remain available while either optional capability is absent.

Local verification uses the same server-owned API/engine, never a second daemon or a direct CLI/SQLite/restic path. The v1.2 policy declares bounded full-read and functional-restore intervals; a v1.1 policy is display-only for qualification. A protected read lease starts one finite mode of the same `vsk-labs` executable through an exact root-owned systemd template. The persistent controller, repository custodian and pinned restic child use three distinct UIDs. The custodian alone owns and opens the repository, revalidates the server-owned lease over authenticated local IPC, and exits at close or lease expiry. The verifier receives typed inventory/results through that channel and proves signed point objects, full restic read and isolated SQLite restore before an immutable local proof or last-good CAS. Later repository objects may coexist with an older point, while missing or changed objects in its manifest deny proof. Fixture and overdue attempts remain visible but cannot advance live last-good. The server proves the pinned binary and current schema catalog from protected local pins. It also has a typed resolver for `config`, `image` and `signature` dependencies: each proof must come from one current, revisioned source, match the exact artifact and bundle digests, verify against the registered trust-root digest and Sigstore identity/issuer, and bind the point, policy, state revision and recovery epoch. The production artifact reader and site source/root registry remain unavailable, so those three kinds still fail closed in an ordinary installation. A synthetic signed fixture proves only the resolver contract. This software flow grants no off-site, media, clean-host or `G-008` authority.

Off-site recovery is a separate optional capability. It admits only a current `local-verified` critical point and creates one independent encrypted generation for that exact point through a credential-bound central effect. Five generation-qualified payload prefixes are protected indefinitely and `locks/` remains mutable. The child receives the repository password and one-run IAM bearer only through sealed descriptors; issuance stops at child exit, and off-site last-good waits for all sessions to expire, exact snapshot/object verification, a current full read, and qualified cutoff denials. Pending, fixture-only, overdue, uncertain, failed, or provider-unavailable off-site evidence never changes local last-good. Manual fallback uses the same point, manifest, generation, rule digest, seal, proof and prior-good identifiers through the approved `vsk-labs` plan/run path; direct R2, restic or SQLite commands do not qualify or reconcile the point. Real provider semantics and clean-host recovery remain `G-008` activation evidence.

Retiring one generation is separately planned as `backup.retire.offsite` with destructive risk and a central infrastructure-admin human acknowledgement. The immutable intent binds the complete pre-rule set, exact five-rule subtraction, exact object inventory, separate lock-admin and retention consumers, one-owner proof, survivor set, bounds, revision and epoch. The rule full-configuration PUT is never described as compare-and-swap. Any ambiguous rule result stops before object deletion; any ambiguous object result remains append-only uncertain. A verified receipt is possible only after every survivor passes its complete rule/object, full-read and isolated-restore checks. There is no scheduler, direct DELETE route, status setter or prefix-wide fallback.

Fixed scheduling never includes retirement or restore. Its closed action set is gate check, observation refresh, backup creation, backup integrity verification and audit checkpoint export. A new or changed cadence, window, target, adapter, credential reference, retention digest, grant, state revision or recovery epoch requires a new inert policy and human activation plan. Expired and stale policies fail closed.

An independent recovery witness is a separate authority from both controllers. Its Ed25519 verification key must be pinned from a protected recovery manifest authenticated by an infrastructure administrator outside restored SQLite and former-controller files. A controller cannot enroll or revoke its own witness. The software verifies a signed, exact recovery-attempt binding, a bounded encrypted custody handoff, a one-use local receipt outside restored SQLite, and complete typed direct-denial transcripts. These contracts do not create a custodian, provision keys, qualify a production denial adapter, or enable a production recovery source. Until an independently administered custodian and every applicable direct-denial probe are qualified, recovery remains unavailable and the replacement stays recovery-required/read-only.

### Independent recovery witness handback

The recovery operator first keeps the replacement in recovery-required/read-only mode and independently establishes the former and replacement host and instance IDs, prior and proposed new epochs, exact draft ID and ciphertext fingerprint, state revision, plan/run/step/lease IDs, fresh challenge and receipt ID. The infrastructure administrator, using an identity outside both controllers, signs a manifest for that *one* binding. The manifest pins the separate witness Ed25519 key and replacement X25519 recipient public key, expires within 24 hours, and is checked against the admin root at fixed protected paths `/etc/vsk-labs/recovery/admin-root.pub` and `/etc/vsk-labs/recovery/witness-manifest.json`. The root and manifest must be root-owned and non-writable by the controller service; a root-running server cannot use this source. Changing or revoking the pin requires a new independent administrator action. A digest mirror in restored SQLite is not a pin.

The custodian holds the signing key and protected material outside the former and replacement controllers. Its finite collection step probes each current, server-derived boundary against the *old* identity, including the alternate host/process path, Mesh re-enrollment, live SSH sessions, secret resolver, every mutating provider adapter, backup writer/session and audit writer. Each independently qualified adapter must return a direct denial response and its own target, observer, challenge, response digest and session expiry. An unreachable target, absent adapter, stopped-service report or generic signed status is not denial. The custodian signs the canonical result; the public signed artifact can be carried to the replacement, while custody material is sent only in an X25519/HKDF/AES-GCM envelope bound to the admin manifest, exact attempt and receipt. The systemd service supplies the replacement's protected `recovery-recipient-x25519-v1` credential; the server verifies its public key against the manifest and does not accept a caller-selected private key.

Issue #153 adds the finite Linux command `vsk-labs recovery witness collect --file <public-request.json> --signing-key-fd <fd> --material-fd <fd> --output json` for a separately administered custodian. The public request carries only the exact binding; the complete boundary set is sealed inside the administrator-signed manifest at fixed protected OS paths. An omitted or altered probe cannot be supplied by the public request. The two distinct inherited descriptors carry the witness signing seed and protected material. The command probes every signed old-identity route through typed adapters, re-probes the signed denial set, and returns a versioned JSON result with a signed artifact and an encrypted recipient-bound envelope encoded separately. It never returns plaintext material. The default production adapter registry is empty: until an administrator independently qualifies every applicable adapter and custodian source, the command blocks, and no recovery source is registered. A build-tagged disposable binary alone registers a loopback-only synthetic adapter inside a disposable root Linux container; its multi-process proof separates custodian, former and replacement OS identities and two host keys. These results are not live denial evidence.

The clean replacement verifies the admin root, exact signed binding, 60-second witness and probe freshness, complete direct-denial set and encrypted handoff; it consumes a durable one-use receipt under `/var/lib/vsk-labs/recovery-witness-receipts` outside the restored database. It must compare the decrypted stream to the exact opened ciphertext inode before allowing #144's recovery transition. If any step fails, preserve the manifest, receipt, source ciphertext and denial evidence; leave recovery-required/read-only in force, investigate the named missing boundary, and start a fresh challenge and independently signed manifest only after correcting it. Never reuse a receipt, copy the old host key, infer denial from controller status, or repair the restored database to force a pass. The current code has no registered production witness source or qualified provider/host/Mesh denial adapters, and #144 owns the exact-inode composition; this procedure describes the required handback, not a live cutover authorization.

The local backup path is similarly scoped to inert input plus pending-only creation. `vsk-labs backup policy draft` stores a canonical policy as an inert draft and returns its digest; the digest binds through one `x-backup-policy` declaration extension, and only the exact human-approved Phase 4 plan/run path may create a point. The current protected profile registers only source ID and selector `control-database`, mapped to the store-owned SQLite Online Backup, and repository IDs `local-standard` and `local-critical`, mapped to their respective protected roots. Unknown source, selector, repository ID or mismatched class fails before the writer lease. Creation captures that exact source through the consistency hook, then requests only the fixed `vsk-labs-backup-custody@<nonce>.service` template. The short-lived same-binary supervisor accepts no caller-selected command, path, UID or repository URL; it authenticates the controller and fresh nonce, launches one custody-UID repository owner, passes the password as a sealed anonymous memory descriptor, drops restic to its separate UID, and returns typed inventory/results. Repository and quarantine directories remain custody-owned and inaccessible to the controller and restic by path. The routine writer cannot overwrite or delete retained objects, and records exactly one **pending** recovery point bound to a canonical manifest and exact expected inventory. A pending point is never local last-good, recovery-qualified, off-site or live `G-008` evidence; independent verification and last-good qualification are owned separately, off-site generation and retirement later still. The local path preserves the prior verified point on every failure and never prunes on capacity pressure, including when declared capacity arithmetic overflows. The distinct-UID systemd/restic lane is disposable Linux acceptance only; installing its accounts, unit, policy or storage on a real host remains a separate infrastructure-admin action.

Local retirement reuses that custody process under a separate retention role. A complete applied retention-lock catalog turns rollback and recovery promises into authoritative point locks; caller flags cannot clear them. A keep-within selection is relative to the latest verified point, and the sole last-good always survives. The immutable intent binds targets, survivors, their manifest/inventory/dependency/proof digests, the full repository inventory, the lock catalog and source coverage, the current revision/epoch and bounded mutation/repack bytes. A new point or catalog activation makes the plan stale. Restic may repack survivor data, so the retention REST role journals every created object and moves every removed object to same-filesystem quarantine. It publishes a new readable repository generation only after the complete post-inventory, mutation journal, full payload read and isolated restore of every survivor agree. A crash, response loss or partial publication preserves the predecessor authority and quarantine for explicit reconciliation under a fresh plan.

The public retirement draft surface never accepts point or object targets. It derives them from current verified recovery points, last-good state, expected objects and the applied lock catalog, then durably stages its one exact credential step binding. Plan creation remains a later action and fails closed if that binding or either named digest extension is absent.

### Local credential import and lifecycle preparation

The human procedure and the CLI have the same boundary:

1. On the control host, verify the protected local server profile, the current state revision and recovery epoch, the qualified systemd host key, and the root-owned `0700` credential-draft directory. Use an individual local OS-peer identity; browser, remote-read and constrained-SSH transports are denied.
2. Prepare the exact public binding: reference, consumer, purpose, target, `native-systemd` resolver, material version and a unique idempotency key. Pass the private bytes only through standard input, or through an already-open descriptor numbered 3 through 1048575 with `--input-fd`. Never place the value in arguments, JSON, an environment variable, a named-file flag or a prompt. Invoke `vsk-labs credential import` with `--config`, those public binding flags, `--expected-state-revision` and `--recovery-epoch`.
3. Treat the returned draft ID, reference ID, ciphertext fingerprint, state revision and recovery epoch as the complete safe result. The command never prints or stores plaintext in SQLite. The append-only row and host-key ciphertext remain inert until an exact lifecycle declaration is planned, independently acknowledged and executed with its current gates.
4. An exact retry with the same idempotency key, epoch and binding returns the recorded draft without reading or replacing private input. A changed binding, stale revision/epoch, missing/corrupt/mis-owned ciphertext, ciphertext without a matching database row, or database failure after ciphertext promotion fails closed. An orphan or mismatch returns `RECOVERY_REQUIRED`.
5. On `RECOVERY_REQUIRED`, stop. Retain the database, ciphertext, audit evidence and command result; do not delete, overwrite, rename into place, edit SQLite or retry under a new key to bypass the conflict. Record the affected draft/reference and follow the [credential lifecycle and recovery procedure](credential-lifecycle-recovery.md).

The ciphertext remains bound to the current systemd host key. This limits ordinary file disclosure but does not protect against root or whole-disk theft when that key is on the same disk. Host replacement still needs independent retained recovery material and authorized re-encryption under a newly qualified host key; copying the old host key is not accepted recovery.

### Clean-host credential recovery boundary

The recover action remains unavailable in production until an independently trusted custody and former-controller fence source is enrolled, every endpoint-specific denial adapter is qualified and the restore procedure establishes current replacement authority. The implemented verifier validates the exact sealed import draft, its ciphertext fingerprint and origin revision, the current recovery epoch, custody/fence evidence digests, the one-use handoff, and the exact opened ciphertext inode against independently supplied material. The ordinary production registry intentionally remains empty. A local database epoch, audit-genesis row, plan digest, fixture or ciphertext file alone is not independent recovery proof. An existing inert draft must be validated as-is; encrypting the same value again creates a different ciphertext and cannot prove the draft's fingerprint.

The human recovery procedure has the same prerequisites and safe stop:

1. Establish the new authoritative control-plane epoch through the separately approved restore/fence procedure. Prove the former controller cannot write, and invalidate its plans, leases, sessions and credentials. Do not let a credential recover command create or advance the epoch.
2. On the replacement host, qualify its own systemd host key and restore material only from independently verified custody. Use the protected local binary import path to create a new inert draft in the already-current epoch; never copy the old host key or ciphertext into the new host.
3. Compare the exact draft ID, reference, consumer, purpose, target, material version, native ciphertext fingerprint, import-origin revision and epoch with the immutable recover plan. Verify independently that this exact ciphertext decrypts under the replacement host key to the retained material, and that the custody and former-controller fence receipts are current and bound to the same epoch.
4. Require a current exact human-approved control-plane plan and the assigned action-scoped execution grant. The recover effect may append only a staged version and recovery evidence; activation still needs its own plan and real positive/denied consumer verification.
5. If any source, key, draft, digest, epoch, decryption or fence proof is missing or disagrees, stop with `RECOVERY_REQUIRED` or `RECOVERY_EPOCH_MISMATCH`. Preserve the database, ciphertext, prior recovery records, audit history and any compromised/revoked status. Do not delete or overwrite evidence, retry an old plan, or treat a test fixture as proof. Resume only through a newly reviewed plan after the independent prerequisite is restored.

Audit chaining is local core behavior; independent checkpoint export is an optional capability. Every new canonical event receives one same-transaction instance/epoch-bound link even when no signer or external store is configured. Existing rows are preserved as pre-anchor history. A selected signer, encrypted append-only writer and separately scoped reader enable exact-plan checkpoint settlement, but their absence reports pending/degraded state and cannot disable local inspection or unrelated work. A proven local/independent conflict is different from provider unavailability: it keeps reads available, blocks mutation as `audit-incident`, and requires the fenced recovery procedure below. The production profile still has no live signer/export composition, so only synthetic independent-anchor tests exist.

## Identity and configuration

Core nodes have immutable logical IDs, verified SSH/access identities and typed provenance. Physical serial, cloud/VM instance identity and installation identity are distinct evidence kinds with explicit issuers/scopes. Serial uniqueness is mandatory only where the selected physical inventory policy requires it; do not fabricate serials for virtual hosts or treat a hostname/IP as identity. Reimage, cloning and replacement require the existing approved binding-change procedure. Names and role aliases are separate; changing a role never silently transfers a person's/device's authority.

A versioned profile supplies validated policy defaults and supported adapter selections; private site declarations supply actual resource bindings and explicit overrides. Resolution order is product safety/support constraints, selected versioned profile defaults, then authorized site declarations within those constraints. The resolved values and provenance are visible in plans. Profile updates produce inert revisioned changes; they never apply infrastructure, enable features, grant permissions or weaken retention automatically. Unknown fields, unsupported capabilities and conflicting ownership fail validation.

Each gate has a stable scoped identity/version, owning layer, subjects, applicability predicate and prerequisites. Core safety gates cannot be bypassed by profile choice. Inapplicable adapter/profile gates display `not-applicable` with the derived reason; this is not a passed evidence result. Enabled-but-unproven requirements remain blocked. Evidence and approvals bind the relevant resolved profile/policy version and existing recovery epoch. The Phase 0.3 profile/gate fixture contract records `fixtureProfile`, `owningLayer`, `profileId`, `profileVersion`, `defaultsDigest`, provenance-bearing `resolvedValues`, versioned `gates`, `requestedOperation`, `slackCapabilityState` and `recoveryEpoch`; its public profiles are exactly `minimal-no-account`, `synthetic-non-labs` and `vegastack-labs-synthetic`. The Labs G-001–G-023 catalog is not a mandatory checklist for other sites.

The Phase 5.3 runtime gate resolver reads only the server-owned applied profile/policy binding; an operator may author a bounded local inert profile draft, but only an exact current human-approved `gate.profile.bind` Phase 4 plan may apply it. Evidence is likewise append-only and recovery-epoch/version-bound, with no stored passed flag. The evaluator registry is deterministic and has no production verifier at this stage: fixture proof and unregistered live proof remain blocked, and a missing applied binding yields no synthetic default profile or successful gate. Read/check projections preserve specific safe blockers while a potentially positive or revision-unbound result stays `subject-binding-unavailable` until a later server-owned collector resolves declaration/revision/artifact for each subject; they never adopt a caller's digest as that authority. The tested attachment-store primitive has no production collector caller yet and cannot make public attached proof valid. The Console consumes generated read-only gate projections; it cannot submit proof, bind a profile, approve, or open SQLite.

## Guided setup and the initial authority

The guided interface offers create-control-plane, connect-operator, enroll-node, and resume/recover journeys through generated metadata. Exact command spellings are finalized in phase 1; a wizard is a client of the existing change/plan/apply engine, never a second mutation grammar. Noninteractive calls require complete typed inputs and explicit authorization; missing input never means automatic yes. CLI, Console and agents receive equivalent plans and errors.

### Local control-plane creation

1. Inspect the selected machine, supported OS/release, installation identity, existing database/service state, privileges, time, disk, dependencies and recovery access. Verify the signed release. An existing or ambiguous installation takes resume/recovery/adoption; never silently reinitialize it. A scan cannot prove a compromised OS clean. Initial OS trust and any reimage decision remain human prerequisites.
2. The administrator nominates this host from a trusted local console, or an already verified SSH session with a usable recovery path. Bind the responsible human and verified OS identity; do not trust an arbitrary email, agent assertion, environment variable or first web visitor. Show the finite initial installation plan and create its one-use Slack approval request.
3. Before SQLite exists, the same engine uses one protected, signed, one-use installation manifest containing the intended operation, approved host/release/administrator binding, selected profile/default provenance, recovery prerequisites, expiry/nonce, initial Slack mapping and logical Slack secret references, exact minimal operations, progress and audit handoff. The configured Slack user must approve the exact manifest digest through an authenticated Socket Mode interaction before consumption. Replacing the file, mapping or manifest cannot authorize itself.
4. A narrowly scoped installation step establishes the service identity, protected paths, authenticated local socket and OS service entry. This is the sole pre-database exception, limited to this host and this manifest, not a generic offline executor. Only `vsk-labs server run` initializes/opens writable SQLite. Use exclusive initialization, ownership/path checks and transactional manifest consumption; a crash never creates two authorities or loses the original approval trail.
5. Start the unprivileged persistent service with local authenticated access only. It imports the bootstrap records and disables further use of the manifest as authority. The same local CLI now calls its API. Public DNS, Mesh, external browser ingress and whole-fleet inventory import are not required merely to start this restricted local service, but normal v1 creation still requires the configured Slack prerequisite.
6. Through separate current plans, establish local hardening, credential resolution, backup/key recovery, inventory and the selected capabilities. Ansible owns host configuration; approved elevation is bounded to the declared work. No root server, broad convenience sudo grant or privileged AI/node agent is introduced. Before risky SSH/firewall changes, arm recovery independent of the executor session.
7. Verify each readiness capability independently. A running local service is not control acceptance, host workload admission or site readiness. The wizard reports remaining evidence, manual prerequisites and next permitted action without declaring a broad success.

The Phase 0.3 installation-manifest fixture names the contract fields: `manifestId`, `releaseBuildId`, `releaseDigest`, `intendedOperation`, `hostIdentity`, `databasePathRef`, `initialAdministrator.localPrincipalId`, optional `initialAdministrator.sshPrincipalId`, `initialAdministrator.slackBindingId`, `profileId`, `profileVersion`, `profileDefaultsDigest`, `profileProvenance`, `stateRevision`, `recoveryEpoch`, `recoveryPreconditions`, `approvalRequestId`, `expiresAt`, `nonce` and `state`. `profileProvenance` carries the provider-neutral source plus the selected typed acknowledgement-adapter extension; the Slack adapter extension holds only the initial workspace/user/local-human mapping and logical secret references. `recoveryPreconditions` carries the typed manifest-integrity prerequisite (canonical digest, detached-verification-bundle format, signer-key identity, verification-bundle reference and verification status) beside other recovery prerequisites. This keeps Slack out of the portable top-level manifest contract. Manifest state is exactly `pending`, `consuming`, `consumed` or `failed`. The setup-transition fixture binds `from`, `operation`, `to`, `manifestState`, `writerState`, `stateRevision`, `recoveryEpoch` and `postconditions`; capability state is exactly `uninitialized`, `local-setup-service`, `foundation-preparation`, `qualified-capability`, `site-accepted` or `recovery-required`. The linked positive cases require the manifest ID, request ID, canonical subject digest, state revision, recovery epoch and workspace/user/local-human mapping to match across the manifest, Slack proof and inert approver import. These are sanitized development contracts, not proof that a server, database or Slack integration exists.

### Preparation versus activation

| State/capability | What is allowed | What remains blocked |
|---|---|---|
| Uninitialized | Account-free read-only preflight and preparation of the finite local installation manifest; consumption only after exact Slack acknowledgement | Database initialization, fleet changes, external provider credentials, public ingress and workload admission without the Slack prerequisite. |
| Local setup service | Authenticated local inspection/planning; exact local hardening, credential and recovery setup plans | Unrelated fleet work and any claim of recovery or security qualification not yet proven. |
| Foundation preparation | Individually approved discovery/bootstrap/hardening of identified foundation nodes once control identity, scoped credentials, retained access and operation-specific recovery are verified | User workloads, CI and broad provider authority until their security/role gates pass. This is not a skip-gates mode. |
| Qualified capability | Only operations whose current OS/role, identity, privilege, recovery and adapter evidence passes | Other capabilities remain visibly pending, even if the local service is healthy. |
| Site accepted | All applicable deployment acceptance including independent probes/restores and actual pilot evidence passes | Nothing gains authority merely from the status; every subsequent mutation still needs its plan/policy branch. |

A local file backup may protect a reversible configuration step but cannot certify independent recovery. When no second probe/restore target exists yet, retain those acceptance blockers and permit only the bounded preparation needed to establish them. Identify that dependency in the plan; do not substitute localhost probes for external denial tests. In the Labs profile the early local setup is followed by scoped LAN/foundation preparation, the actual Mesh pilot and control/site qualification. The full software must still be complete before the first live onboarding rehearsal.

### Interruptions and controller self-management

Durable run events and observed postconditions decide what happened. Re-running setup queries that state; it never blindly repeats a provider mutation, resets an admin or reinstalls a database. Unstarted plans expire after the existing 30 minutes. A run begun in time may retain its identity only under the documented same-epoch resume rule; changed facts, privileges, scope or epoch require a new plan. Revoke the human/device and continuation must stop.

Controller-local Ansible is an explicit OS-profile execution mode for approved control-host configuration; other nodes retain SSH/Ansible. Its invoking identity and actual privilege boundary must be proven, not inferred from a sudo command list. Ansible's local connection does not use a remote-user setting, and its reboot action refuses local-controller reboot. Controller reboot/upgrade therefore checkpoints the exact run and boot identity, schedules the approved OS action, starts the existing service after boot, verifies persistence/health and reauthorizes continuation. Never implement it by pretending localhost is an independent remote executor. [Ansible local connection](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/local_connection.html) · [reboot action](https://raw.githubusercontent.com/ansible/ansible/stable-2.19/lib/ansible/plugins/action/reboot.py)

Disk-full, corrupt database, unknown schema or missing recovery material produces a visible recovery state, not automatic initialization. Access rollback uses the native OS timer/service facility and survives the failed session; local console recovery remains necessary when the OS cannot boot or networking is irrecoverable. No operator machine self-promotes when control is unavailable.

## Operator and managed-node enrollment

**Operator:** install a supported client, verify the selected instance through a trusted channel, authenticate an individual identity, and obtain explicit device/person scopes. Local OS-peer and constrained SSH identities map to the same effective grants as external identities. Store client material using the existing OS credential abstraction. Invitations are short-lived, single-use and bound to instance/device/intended scope; possession alone cannot grant administrator status. Never copy SQLite, fleet keys, provider tokens or another user's AI login. Different devices are separately revocable.

**Managed node:** from control, inspect an explicitly authorized reachable target, bind node/provenance/SSH identity, select a supported role and plan minimal bootstrap access, Ansible hardening and qualification. An optional local `vsk-labs` enrollment helper can verify the controller and present evidence, then exit; it grants no persistent privileged agent or self-selected role. Missing Python/SSH, unknown host key, offline host and Mac consent are explicit prerequisites, not assumed success. Operator enrollment and managed-node enrollment are separate even on one device.

Unsupported OS/provider/role combinations are rejected before mutation. A physical host and a qualified VM may use different identity evidence; verification must match the actual profile. Existing services remain observation-only until an import plan establishes one owner and explains every change. No full provider account is adopted merely because one service was imported.

The `host-security-v1` admission profile makes the bootstrap/admission boundary executable. Minimum SSH or local-console access may discover and prepare a host, but it cannot admit a role. Admission requires the exact supported OS/architecture profile, every applicable common and role control, a current release/build and declaration revision, the current recovery epoch, daily and after-change evidence, independent recovery and a second idempotence/reboot proof in the implementing phase. Unsupported or incomplete hosts remain quarantined.

The account-free native credential lifecycle is `cold start → bind one logical reference to one consumer → resolve only after authorization → verify without returning material → rotate and verify the new version → revoke the old version → retain independent recovery`. Cloud identity and TPM-class hardware are optional profile capabilities, never portable prerequisites, and their absence never permits plaintext fallback. `continue-existing-workload` preserves a safe running workload when evidence merely becomes stale; `recover` remains available only through its separately authorized recovery path. Neither operation admits new work, expands a role or issues a new workload credential.

## Effective authority and revocation

Desired declaration revisions remain inert. Authorization, timers and capability admission consult only the effective policy/grant/profile state, never a proposed row. A change is authorized under the prior effective authority and cannot authorize itself. Persist the desired/applied/effective distinction and partial outcomes. Expansion becomes effective only after the approved transition and required verification; approved denials become effective at their declared containment boundary and are not undone merely because another target failed. Read scope permits inspection/preview without committing intent; committing a draft/plan requires author scope.

Offboarding enumerates independently authenticated local and configured application/provider accounts, keys and sessions, including active sessions rather than only future logins. Use existing scoped adapters or an assigned human/app owner; do not acquire extra privileges for Harbor or another application. Persist every unresolved revocation. An approved offboarding plan may include bounded isolation, preserving administrator recovery access; an unreachable target remains uncontained/pending until verified. Reconnect requires reconciliation before readmission. Routine secret rotation may preserve a healthy old credential, but an approved compromise-containment decision takes precedence and must never be rolled back to regain availability.

### Human acknowledgement trust boundary

An OS UID, SSH key or cached browser session proves an authenticated account, not whether a human or an agent sharing that account made the request. Agent/session labels, a TTY and a typed yes are not human-presence proof. This limitation applies to Codex/Claude as well as Hermes, including the initial installation acknowledgement. Never label those mechanisms alone as server-enforced prevention of agent self-approval.

Delegated agent credentials have no acknowledgement scope. Where ordinary account credentials are available to an agent, human acknowledgement additionally needs a separately protected human action/proof unavailable through those credentials, bound to the exact plan/installation manifest, targets, expiry and recovery epoch. Replaying a login or an old acknowledgement is insufficient. The server rejects missing/unqualified proof rather than accepting self-reported actor type. An approved exact-policy run remains its separate branch, never a human impersonation.

V1 selects Slack as its only normal human-acknowledgement adapter and accepts the resulting third-party account/network prerequisite. `vsk-labs server run` verifies the authenticated Socket Mode envelope, workspace/team, configured Slack user, action/request ID, freshness, nonce and current local authorization before recording a provider-neutral proof. The Phase 0.3 fixture names `requestId`, `requestKind`, either `planId` or `installationManifestId`, `subjectDigest`, `targetSetDigest`, `reasonDigest`, `riskClass`, `responsibleHumanId`, `workspaceId`, `slackUserId`, `action`, `envelopeId`, `receivedAt`, `expiresAt`, `nonce`, `stateRevision` and `recoveryEpoch`. Its `sessionControl` value is a test precondition for the approved threat assumption, never a client assertion or authentication signal. A changed field or replay is denied; redelivery of the same already-consumed action is idempotent and cannot create a second acknowledgement. The threat assumption is that the assisting process cannot operate the approved user's Slack session, preferably held on a separate phone.

A private approver configuration maps Slack workspace/user IDs to local human principals and allowed approval classes. Its inert import contract names `workspaceId`, mappings of `slackUserId`, `localHumanPrincipalId` and `approvalClasses`, `priorEffectivePolicyRevision`, `proposedRevision`, `authorizingApproverId` and operation. It contains no Slack token or signing secret, stays outside Git and imports only as inert desired state. Adding or widening a mapping requires an already effective infrastructure administrator's Slack approval; a proposed user cannot approve their own addition. Removal/revocation invalidates outstanding requests according to policy. The provider-neutral request/proof and Slack orchestration belong to issue #7; identity mappings to #9; logical secret references/delivery to #12; review/approve/reject presentation to #15. Issue #14 notification delivery cannot acknowledge or authorize a plan.

Acceptance runs an adversarial process with every ordinary credential available to the coding agent: local/SSH/browser acknowledgement attempts, omitted/forged agent context, wrong workspace/user, substitution and replay must fail without the verified Slack action; duplicate delivery must be idempotent. Missing/unavailable Slack or loss of all approved users blocks normal bootstrap/apply. Explicit break-glass recovery is separately authorized, recovery-epoch changing and conspicuously audited; it is never an automatic or routine approval fallback. Account-free human approval is deferred beyond v1. [D-122](decisions-and-sources.md#d-122)

## Recovery and retained dependencies

A recovery point includes its required release/schema, configuration, images/digests/signatures, data consistency method, key references and independent verification history. Preserve those dependencies while the point or rollback promise is retained; the active-plus-two binary cache does not cap the recovery archive. Block unsafe garbage collection or surface a capacity decision instead of silently breaking the recovery promise.

When restoring behind an independent audit checkpoint, recover and verify the missing audit suffix where possible, without replaying its provider mutations. Otherwise require explicit human acceptance of a named lost interval and create a new recovery segment anchored to the prior independent checkpoint and recovered database hash. Preserve both histories; never reuse sequence identities ambiguously or overwrite the newer export. Invalidate old plans/sessions, revalidate grants and fence the former instance before restoring mutation authority. A mismatch without this authorized continuity procedure stays read-only.

Control-authority replacement is a two-startup transition owned by `vsk-labs server run`. The current authority creates an immutable, human-acknowledged restore plan and stages a fixed sibling candidate. After the former service is stopped, replacement startup exclusively locks the database path, verifies the exact transition journal and candidate instance/epoch/audit genesis, preserves the former file, and promotes the candidate as `recovery-required`. A later exact canary is the only transition back to `ready`. Old plans, acknowledgements, browser sessions, leases, credential material and execution receipts remain bound to the prior epoch and cannot cross that boundary. Any ambiguous startup, journal, fence, audit, backup or canary result preserves both histories and leaves mutation disabled.

For backup adapters, mutable coordination objects and retained payload dependencies are distinct. Qualification must prove refresh/unlock/stale-lock behavior, concurrent exclusion and payload protection for the full lifetime of retained points, including deduplicated older objects. The selected restic/R2 candidate is not design-closed until a compatible permission/retention layout is proven. If it cannot meet the agreed safety contract, return a concrete alternative for review; never broaden writer payload deletion, disable locking or silently shorten retention. Exact site resources and real integration evidence remain later gates.

## Disable, detach, replace and uninstall

These are different operations. Disabling a capability stops new work but does not delete resources or revoke credentials still needed by active work/recovery. Before disconnecting an adapter, enumerate dependencies, drain or stop runs, identify retained recovery dependencies, transfer explicit ownership and preserve a human recovery path. Unavailable/unsupported migration becomes a blocker with a documented handoff, not invented conversion. Revoke only platform-owned scoped credentials and verify denial.

Default product uninstall preserves application data, externally managed workloads, audit and recovery artifacts; it removes only the explicitly selected owned installation components after a reviewed plan and handoff. Destruction requires its own target list, recovery preconditions and stronger confirmation. Local account offboarding preserves homes per policy. Physical custody, media sanitization/destruction, repair handoff and disposal are outside product scope; logical inventory and credential retirement remain included.

## Public build and generic experience

The chosen VegaStack Design System and product branding remain. Ordinary public checkout builds and tests must require no VegaStack private account, registry token or access to its private network. Declared public dependency downloads are allowed; this is not an air-gapped build promise. Use approved redistributable pinned component source/public dependencies; validate distribution rights before publishing. Authenticated maintainer component refresh and protected release/integration jobs are separate from public contributor checks. No fork receives private credentials or official signing authority.

Views describe nodes, hosting resources, identity bindings and capabilities; adapter views may show provider-specific detail. Distinguish empty, unconfigured, disabled, unsupported, unhealthy, stale and policy-blocked. A basic installation with zero nodes and no optional adapters must provide a useful next action, not simulate integrations or render an outage. A second synthetic deployment uses different identities, names, size and applicable policy values without changing core code. It tests portability; it is not evidence for an unimplemented production provider.
