# Host action preparation

Preparation is an inert bundle, not permission to install it. Initial installation uses an already authorized administrator at an independently verified console. Normal automation subsequently invokes only `/usr/local/bin/vsk-labs host-action-once` through the exact non-root account's sudo rule. The server public key goes on the target; its private signing key does not.

Before installation, verify machine identity, independent console recovery, the signed executable digest, reviewed role assets, exact automation UID/GID/home and public-key fingerprint. Preserve unknown accounts, groups, keys, sudo grants and configuration. Refuse conflicting existing files instead of overwriting them. Inspect every destination and ancestor for symlinks, ownership and group/world writes. The preparation role is not an automatic bootstrap path and must never run through broad target Ansible `become` in the ordinary action workflow.

Install the verified executable root-owned at `/usr/local/bin/vsk-labs` (0755), the generated public policy at `/etc/vsk-labs/host-action.json` (0600), and the exact sudoers entry at `/etc/sudoers.d/vsk-host-action` (0440). Run `visudo -cf` against the candidate sudoers bytes before atomic installation. Existing files must match the reviewed bytes; `force: false` alone is not verification. State directories `/var/lib/vsk-labs/host-action` and `/var/lib/vsk-labs/access-rollback` are root-owned 0700. Validate the normal user cannot modify any executable, policy, state, unit or ancestor or use unrelated sudo commands.

The only added systemd units implement local access rollback: a one-shot restoration service, its exact 600-second timer, and a boot reconciliation one-shot before SSH/Docker/network policy. They run the same executable's finite `access-rollback` mode with no caller-selected paths or commands. A baseline apply snapshots and synchronizes only its owned files/chains before arming the timer. A signed confirmation is accepted only after independent current probes; a lost controller leaves rollback armed. A reboot while armed restores the old owned state. An uncertain external modification is preserved and requires console recovery.

This does not delete accounts, reset passwords, format disks, flush shared firewall tables, restart the physical host, grant workload admission or permit access to protected nodes04/05. Native acceptance occurs only in a separately approved disposable environment.

## Supported native observations

The protected profile lock must name the actual Debian image, Debian13.6/amd64, executable version and exact installed versions of at least `openssh-server`, `iptables`, `sudo`, `passwd` and `systemd`. Runtime checks these facts, declared interfaces/addresses and local account identities before writing. Unsupported SSH socket activation, conflicting drop-ins, active competing UFW/firewalld ownership, unexpected interface addresses, unsafe existing homes/keys or privilege-bearing group membership refuse without modifying the conflict.

The installed sudo component supplies `cvtsudoers` JSON. The fixed converter invocation expands aliases and includes and matches the local account; only the exact helper grant is accepted. Extra grants, unknown policy/plugin/source configuration and broader commands remain unqualified. There is no parallel sudoers parser or policy-approval registry. The command and JSON shape are grounded in [Debian's cvtsudoers manual](https://manpages.debian.org/trixie/sudo-ldap/cvtsudoers.1.en.html); actual native converter execution is part of the separately authorized qualification.

Privileged service keys use `/etc/vsk-labs/service_authorized_keys/root`, independently of ordinary account keys. Each key is explicitly declared, source-restricted and has no PTY or forwarding. Human/automation fingerprints cannot double as service keys. A declared service key may retain its narrowly scoped root command access (the Labs profile uses this for Coolify); it does not grant root access to human keys or the ordinary helper account. Unknown existing root keys or conflicting restrictions stop the change for review.

Private source/container contexts are installed separately in `/etc/vsk-labs/access-probe-contexts.json`, root-owned0600 or0640 with only an existing dedicated service group allowed to read. Preparation must verify each exact host/context/container identity and any network-namespace mapping. Ordinary baseline actions do not create these contexts or discover arbitrary containers. Subject collection can carry actual scoped Docker address ownership before baseline admission; this does not claim that unapplied access controls passed.

A successful pre-Docker baseline action may carry `debian.container-firewall` as `partial` / `container-not-installed`. No Docker chain is invented and no container admission follows. Required container probes cannot be omitted from an acknowledged plan. Role installation must supply fresh applicable collection and allowed/denied container probes before admission.

Initial preparation creates a missing dedicated automation account only after checking its exact UID, primary GID, unused home and existing privilege conflicts. It installs an automation-only `Match User` SSH drop-in and its declared public key so the later signed baseline does not depend on a helper that cannot yet be reached. Other users' SSH policy is not widened. Existing conflicting account/home/assets refuse. This initial SSH reload belongs to the separately authorized administrator preparation, never ordinary self-installation. Verify a fresh automation session and independent console before leaving that procedure.

Ordinary root-owned public-key files are0644 under root-owned0755 searchable `/etc/vsk-labs/authorized_keys`; the policy itself remains0600 and receipt directories0700. OpenSSH opens these public-key files under the authenticating user's UID, so making every ancestor0700 would break authentication. [OpenSSH's key-file check](https://github.com/openssh/openssh-portable/blob/master/auth2-pubkey.c). Public keys grant no filesystem write authority. The root-only privileged service key directory remains0700.
