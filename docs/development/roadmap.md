# Full-scope development roadmap

Status: draft for user review, prepared 26-08-2026. The user has adopted the [operating mandate](operating-mandate.md) and directed that the entire documented scope be delivered phase by phase, with multiple issues per phase. The phase boundaries below are proposals, not approved issue batches or execution authority.

## Scope and finish line

Cover the accepted v1 portable platform, selected adapters, VegaStack Labs profile, operator experience, safety, verification, distribution, and runbooks. Do not reduce the project to a CLI prototype or omit operational acceptance. The existing [specification map](../../README.md#documentation-map), decision register, support matrix, and deployment gates remain authoritative.

There are two distinct completion claims:

- **Development complete:** the specified software, documentation, packaging, and required platform/integration tests pass. Fixtures are identified as fixtures; required real-platform evidence cannot be replaced by cross-compilation.
- **VegaStack Labs accepted:** the existing deployment phases have their real site/provider evidence, authorized operations, and recovery demonstrations. Software completion alone does not satisfy this claim.

Existing exclusions remain excluded: Chaabi Prod migration, general application-by-application placement, Kubernetes/Swarm, distributed storage or automatic stateful failover, Workspace account/licence provisioning, a generic plugin framework, and a custom privileged managed-node agent. Optional mechanisms in the GitHub dependency matrix or D1 discussion do not automatically become mandatory features or enabled integrations. Their enablement must be explicit; disabled optional integrations must not disable local core operation.

## Planning and sequencing

Plan the whole scope here, then detail one phase at a time. The proposed order follows the foundations needed by later phases. Before each batch, replace broad dependencies with exact issue links and confirm the actual interfaces and verification inputs. Independent work is parallel only when the batch explicitly permits it.

Each phase gets `phases/00-<name>.md`, `phases/01-<name>.md`, and so on, containing requirements, solution, exclusions, execution defaults, issue index, acceptance owner, and approvals. Issues use `0.1`, `0.2`, `1.1`, etc. The issue families below are decomposition guidance, not published issues or frozen implementation steps.

Security, tests, documentation, and recovery accompany the capability that needs them. The final acceptance phase integrates and rechecks those obligations; it is not where safety work begins. Later capabilities extend their CLI/API/Console surfaces in their own issues.

If a later phase supplies a required safety dependency, the public command remains blocked until that dependency exists. Synthetic adapters, identities, evidence and release artifacts are isolated test inputs, never a shipping bypass switch. Earlier phases may prove a specifically bounded contract without claiming the complete live workflow.

## Resolve before the affected issues become ready

| Finding | Required planning treatment |
|---|---|
| Root instructions broadly restrict GitHub/provider mutations, while the adopted mandate expects normal autonomous development. | Phase 0 proposes and integrates an explicitly approved development-only boundary; no assumption that mandate adoption grants repository administration, releases, or fleet access. |
| Audit metadata is generated but no generator is present; old reports/hashes describe a historical specification. | Phase 0 establishes provenance and reproducible validation/generation ownership without fabricating evidence or hand-editing generated artifacts. Fix broken documentation links through their source. |
| Some bootstrap prerequisites ask for recovery/install proof of components not yet installed. | Reconcile bootstrap entry evidence versus post-install acceptance before phases 4–6 issue approval, preserving recovery safeguards and exact authorization. |
| Tunnel candidates are named as application nodes but are also documented as the clean spare and unassigned reserve. | Reconcile the role/placement contract before phases 6–7; do not silently repurpose spare capacity or place credentials on a supposedly clean spare. |
| A loopback-only Console origin must be reachable by its intended Tunnel connector, and control ingress is needed before the broader deployment-phase-5 ingress rollout. | Specify the actual protected ingress path and scoped bootstrap order before the affected access/bootstrap issues; preserve direct-origin denial. |
| Several contracts require precise executable details rather than high-level terms: canonical serialization, idempotency, session/lease renewal, pagination/events, and evidence freshness. | Settle the relevant details in phases 1–5 solution/issue planning. Preserve existing closed values such as the 30-minute plan validity; ask only about genuinely unresolved consequential choices. |

These are planning tasks, not a request to re-interview the entire architecture. Agents should propose evidence-backed resolutions; the user confirms material changes during the corresponding phase/batch review.

## Inputs and approvals, at the right time

**Next confirmation:** review these phase boundaries and complete scope allocation. Then brainstorm phase 0's requirements and solution and approve its first issue batch. Phase 0 is a proposed foundation phase, not an assumption that the user chose a minimal-CLI-only objective.

**Before remote execution:** obtain explicit authorization for named-repository development and separately any proposed repository-policy change. Inspect current rules; agree the normal PR/check/review/merge route without bypass. No new credentials, settings, issues, milestones, release or infrastructure actions are authorized merely by this roadmap.

**Later, only when needed:** obtain unavailable real OS/test lanes and signing identities, actual provider/secret/recovery ownership, site/physical measurements, alert recipients, Harbor migration inputs, and service mappings at their affected gates. Discover facts read-only where permitted before asking the user. Never put private evidence or secret values in GitHub.

Execution estimates belong to each detailed phase/batch once issue scope, dependencies, test runtime and available environments are known. Use the mandate's agent-minute basis and 2× checkpoint; do not invent precise estimates for this unimplemented full-platform roadmap.

## Path to the first completed issue

1. Confirm or adjust this roadmap; keep existing architecture choices unless a demonstrated conflict needs resolution.
2. Create `phases/00-development-foundation.md` with requirements, solution, exclusions, exact exit proof, shared setup and proposed issue index.
3. Review the first batch's complete issue bodies and verification approach with the user.
4. Establish the explicitly authorized bootstrap delivery route and publish the agreed GitHub issues/milestone. Existing labels can be reused.
5. Execute one small approved issue end to end: claim, implementation, deterministic checks, fresh review, permitted merge, final verification and implementation comment.
6. Use any concrete pilot findings to improve the template, finish phase 0, and continue phase by phase. Do not create a speculative detailed backlog that must all be rewritten later.
