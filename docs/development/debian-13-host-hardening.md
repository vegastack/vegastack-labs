# Debian 13 host-hardening reference and disposable test strategy

Status: Issue [6.2 (#214)](https://github.com/vegastack/vegastack-labs/issues/214) records the selected **development design** in [D-126–D-130](../decisions-and-sources.md#d-126). This reference specifies later implementation and qualification obligations. It is not an Ansible playbook, a tested host profile, an admission result or authorization to contact a machine.

The accepted `host-security-v1` fixture pins `debian-13-amd64` to Debian **13.6** on `amd64`; an observed 13.7 or later installation is not automatically qualified. [Debian currently lists 13.7 as its latest 13.x point release](https://www.debian.org/releases/). The owning profile implementation issue must choose and test an exact image/release, then update the approved contract through its normal change path. Existing machines must be inspected before any adoption or reimage; no disk erase, major upgrade or account removal follows from this reference. [D-116](../decisions-and-sources.md#d-116) · [D-117](../decisions-and-sources.md#d-117)

## Profile settings and owners

All paths below name package formats or intended owners. An installed package, valid file or authored success result cannot pass `host.hardening-baseline` or `host.role-admission`; both gates remain deferred until Issue 6.8 binds current applied host facts to the exact identity, OS/build, architecture, role, declaration and recovery epoch. Actual package versions, unit activation and effective behavior require disposable Debian qualification.

| Control | Debian 13 package and service | Configuration owner and format | Required later proof |
|---|---|---|---|
| Individual accounts and scoped automation | native account/group tools; `sudo` only for the approved one-shot boundary | `vsk-labs` declaration selects identities and groups; Ansible applies native account state; root-owned sudo rule names only `vsk-labs host-action-once` with its internal immutable-bundle checks | individual/automation separation, denied shared/wrong account, protected homes/keys, no broad `NOPASSWD: ALL`; preserve unknown accounts for review |
| SSH | `openssh-server`; packaged `ssh.service` / `ssh.socket` | reviewed `/etc/ssh/sshd_config` drop-in or equivalent packaged include, plus declared keys and source policy | validate syntax and effective `sshd -T` under relevant connection context; new allowed session; deny password/root/wrong user/wrong source; retain the separately scoped Coolify privileged key and console route |

## Privilege, firewall and recovery sequence

1. `vsk-labs` reads supported facts and a revisioned declaration, prepares an exact plan and applies only after the required human acknowledgement and recovery precheck. The dedicated non-root automation identity runs read-only Ansible tasks without broad `become`. A root-owned, non-resident `vsk-labs host-action-once` validates its immutable bundle and performs only the approved privileged action. [D-123](../decisions-and-sources.md#d-123)
2. Before changing SSH or host/firewall policy, preserve the last validated target-specific configuration and arm a root-owned local systemd one-shot rollback service/timer with a ten-minute deadline. The later implementation must prove the effective deadline, persistence through controller loss and intended behavior on reboot; a transient in-memory timer alone is not sufficient. The rollback action restores only the affected validated state, never broadens unrelated policy.
3. Apply the exact declared change. Host-input rules are distinct from Docker-forwarded traffic. `DOCKER-USER` restrictions run before Docker's published-port accepts and match the translated container tuple after DNAT; an original-destination match requires an explicit reason and measured behavior. Established responses and approved flows remain possible. Docker-owned rules are not edited or flushed. Fail2ban can ban only the SSH host-input path for at most 600 seconds per event, with an audit event and exact recovery-source exclusion. [D-126](../decisions-and-sources.md#d-126) · [D-127](../decisions-and-sources.md#d-127)
4. Open a **fresh** independent administrator SSH connection, prove declared allowed traffic, then probe wrong user/source and unpublished/east-west denial. Cancel rollback only when all probes pass and the local timer state is verified. If contact is lost, leave the rollback armed and keep the host unadmitted. Ansible `rescue` does not run for unreachable hosts. [Ansible block error handling](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_blocks.html) · [Debian systemd timer semantics](https://manpages.debian.org/trixie/systemd/systemd.timer.5.en.html)
5. After Docker/Coolify role installation or any relevant change, repeat the firewall and SSH probes; after a required reboot, repeat the full applicable control set and apply the same declaration again to prove no unplanned change. Recovery is recorded separately from successful onboarding.

### Qualification still owned by later implementation issues

- **6.5/6.7:** prove exact Debian image/package versions, SSH journal/file backend and source attribution, iptables-nft alternatives and Docker Engine/backend, translated-container-tuple matching in `DOCKER-USER` (or a measured original-destination exception), startup/restart order, actual rule persistence, control-specific audit/AppArmor scope and bounded resource settings on an approved disposable VM. A failing combination remains unsupported, not silently swapped to another firewall manager.
- **6.7:** fault-inject unreachable SSH, controller loss, ten-minute timer expiry, reboot and failed allowed/denied probes. Verify local rollback and retained console access. The exact systemd unit implementation must be checked against the target's service/timer semantics, including timer accuracy and reboot behavior.
- **6.8:** bind every positive host gate to current applied identity, exact OS/version/architecture/role/profile, verified control facts, declaration revision, freshness and recovery epoch. Schema-valid or generic gate evidence alone cannot admit a host.
- **6.9/6.12:** repeat role and recovery probes after service installation, replacement/reimage and integrated qualification. Existing production-like machines and inventory nodes are outside these development tests.

## Disposable development test targets

Use an isolated full Debian 13 `amd64` VM per exact profile candidate, with a snapshot before hardening and separate virtual sources for permitted administration and prohibited login/network probes. The VM's network must not bridge to the inventory LAN, application-hosting network or existing site Mesh; any egress needed for signed package downloads is narrowly reviewed. Supply no fleet credentials, application data, production volumes or real service endpoints. Snapshot/revert for fault injection, retain sanitized logs and verification results, then destroy the disposable disks. Containers are useful for unit/contract checks but cannot establish systemd boot, kernel firewall, audit, AppArmor, SSH lockout or reboot proof. [D-130](../decisions-and-sources.md#d-130)

This is a target **strategy**, not permission to create a VM. Before any provisioning or test, the operator must explicitly approve the named development host, VM count/resources, network isolation, test commands, data handling, teardown and any spend. No inventory fleet node or existing application host is an implied target. The temporary Issue #81 CI-host exception, where applicable, is limited to its named public development checks and is not host admission evidence.

Mac mini and iMac enforcement, consent, recovery and isolated test-target selection remain in a **later Phase 6 batch within v1**. Existing Mac roles, D-107/D-124 and complete v1 acceptance remain in force. Neither Mac is contacted or used by this strategy. The later batch must bring its own approved scope and separate test-target authorization; a disposable account on an app-hosting Mac cannot isolate system-wide SSH/firewall changes.

The [Phase 6 development plan](phases/06-host-lifecycle-bootstrap.md) records the approved 6.3 discovery batch and later qualification ownership. This research reference does not grant approval for those later batches.
