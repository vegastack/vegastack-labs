# Linux host replacement

Host replacement preserves the former machine's immutable identity and records alias ownership changes in the server-owned control database. It uses the existing declaration, plan, human acknowledgement and run APIs. Reimage or OS installation is an independently completed human prerequisite; this workflow never formats a disk or initializes over an existing database.

The supported restoration classes are `stateless-role` and `control-database`. Stateful applications, provider-owned resources and unknown credential consumers block replacement until their owning integration supports them. A moved alias does not move workloads, change routing, rotate provider credentials or admit a machine. Native qualification belongs to issue #228; this implementation does not establish it.

## Prerequisites

Resolve old host, replacement host, aliases, credential consumers, observers, recovery source and custodians from already available applied records. Nodes04/05 remain entirely excluded, including indirect effects. Infrastructure operations require their own named target authorization; development approval is not that authorization.

Both hosts need current registered immutable identities, pinned target keys and exact declared Linux roles. Copied machine identities or keys cannot become a replacement. The replacement needs an independently observed administrator-prepared OS, suitable architecture/capacity and current baseline/role evidence. Control recovery additionally needs an actual verified compatible source, independent recovery custody, an unused protected candidate destination, installed recovery qualification and the existing single-writer transition.

## Procedure and equivalent human fallback

1. Inspect the current registered identities, desired role declarations, applied profile and proof status using the existing API. Record blockers individually. Initial aliases must first be claimed through an exact `host.alias-claim` declaration carrying `hostAliasClaim`, followed by its own plan, human acknowledgement and run. Inventory alias text does not establish ownership. Only unowned aliases may be claimed.
2. Submit `HostReplacementRequest` to `POST /api/v1/host-replacements` with `operation: freeze`. The server resolves both hosts and current owner revisions, checks the exact proposed role declaration and stores an inert draft. It returns its declaration ID. Preparation does not freeze or contact a host.
3. Prepare and inspect the existing readable and JSON plan. Obtain the assigned human acknowledgement and execute the exact plan through the normal run API. The freeze prevents new admission, action signatures and affected execution reservations on the former identity. It retains ownership history and existing data. It does not stop a workload or cancel a previously dispatched native action merely by changing database state.
4. Resolve every outstanding continuation and all owned credential consumers. The final ownership transition requires fresh independent denial through the already installed qualified adapters. An unreachable host, expired challenge, database revocation or administrator assertion is not a denial result. Unknown or shared consumers block the narrow replacement.
5. For `stateless-role`, use the existing exact role preparation, acknowledged install and fresh collection flows on the replacement. The complete owned payload set must be empty. Report a rebuilt role, never restored application data. For `control-database`, use the existing restore plan/run APIs. Planning derives bounded continuity from the actual verified snapshot and current authority. Before candidate writes, the server measures verified snapshot bytes, available space and preserved database/WAL/SHM files, and refuses insufficient space or occupied/unsafe candidate paths. The candidate carries the newer ownership history and remains recovery-required. Normal startup promotes it under the existing writer lock; the existing verification/canary workflow must complete after reopening. Never run setup on the recovered candidate.
6. Recheck current identity, baseline, role, network, volume recovery and applicable native qualification using the common admission evaluator. Submit the same immutable replacement intent with `operation: commit` and current revision/epoch for a fresh plan and human acknowledgement. Its execution obtains fresh qualified denial and atomically compares all frozen owner revisions, proof bindings, approval and execution lease. Every named alias moves or none does. The former host remains frozen/retired even if it returns online.
7. Read `GET /api/v1/host-replacements/{replacementId}`, the exact run receipt and sanitized audit. Verify the new owner and retained historical owner for every alias. Absence of future provider qualification remains a blocker to workload admission.

The human fallback follows these same commands, prerequisites, target limits and approval branches. It is not a raw SSH, database-edit or provider-CLI shortcut. On interruption, inspect the durable stage and original run; preserve source, candidate, journal and owned-file preimages. Reconcile uncertain native work with its existing acknowledged verification flow. Never delete a journal to force retry or automatically restore the former host's authority.

## Recovery continuity and failure behavior

Restore planning reads the alias watermark from actual verified snapshot bytes. It carries all newer alias changes, including unrelated aliases, together with the exact frozen replacement history. The carrier is bounded to 32 affected aliases and 256 ownership events; overflow, omission, conflicting history or missing current authority blocks the attempt instead of truncating evidence. It carries no grants, credentials, acknowledgements or host qualification. Missing registration rows after an older restore require ordinary current reconciliation.

Candidate verification reads back the actual carried rows. A restore with no alias history still inspects the verified source. The empty-history branch requires the original ready authority and empty ownership tables; a recovered or recovery-required database with missing history cannot assert that no newer owner existed. Such an attempt needs authenticated current continuity and remains blocked when it is unavailable. Unsupported snapshot inspection also blocks planning. An attempt with current ownership history cannot bypass continuity merely by omitting the optional reference. Source or credential failure, denied qualification, concurrent replacement, stale revision/epoch or alias comparison failure leaves a blocked state with preserved data and former ownership history.

The public Console and CLI guided workflow is owned by issue #239. These operator-local API contracts do not create a browser authorization path.
