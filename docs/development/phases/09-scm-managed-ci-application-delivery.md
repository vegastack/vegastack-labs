## Outcome and approach

A trusted application revision can build, produce verifiable image/provenance/SBOM evidence, publish to its registry scope, and reach the existing exact-plan deployment executor. Build jobs and deployment jobs have separate credentials. The existing `vsk-labs server run`, server-owned SQLite, protected credential resolver, declarations, plans, acknowledgement and executor leases remain the authority. Add no second controller, queue, privileged managed-host agent, generic CI framework or signing service.

The Labs GitHub adapter is replaceable. GitHub outages cannot disable local control reads, plans or recovery. Optional repository discovery, webhooks, rich statuses and Apps remain unselected; they are not prerequisites for the first working path.

## First delivery contract

`internal/ci` compares an explicit enrollment against a fresh observation. It binds stable repository/owner/workflow IDs, repository name, workflow path and SHA256 file digest, immutable source revision, exact branch ref and event, assigned job name, runner/group IDs and label set. This first slice supports only exact `push` or `workflow_dispatch` branch bindings. Pull-request/fork events, wildcard identity and missing/mismatched inputs are denied. Every other event remains unsupported rather than being treated as trusted.

`Match` returns only `enrollment-match`; it is an inert comparison with no credential, runner-admission or deployment authority. Observation age is limited to 60 seconds, with at most 5 seconds of positive clock skew. The caller supplies current time explicitly. No durable admission proof, alternate policy store or caller-writable execution grant is created.

`internal/adapter/githubci` reads a configured HTTPS API origin using fixed constructed routes. It checks the current run before and after observing the exact run attempt, complete bounded attempt-job membership and the actual workflow file at the pinned revision. Stable repository and head-repository IDs must agree; runner labels alone cannot prove the assignment. Provider-returned URLs are never followed. The REST contract is pinned to `2022-11-28` for this software slice.

The adapter borrows the existing `credentialref.Value`; nil explicitly selects public reads. It never discovers a credential from an environment variable. JSON, page count, workflow bytes and overall request duration are bounded, duplicate keys are rejected, redirects/retries are disabled, and returned errors contain fixed categories without provider bodies or tokens. A configured transport is a trusted composition input, never a job option.

Official contracts checked on 27-10-2026: [workflow run attempts](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run-attempt), [attempt job membership](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt), and [repository file contents](https://docs.github.com/en/rest/repos/contents#get-repository-content). The [runner hook documentation](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/run-scripts) describes before-step hooks and nonzero-exit denial; those documented capabilities alone do not prove an immutable guard, hostile-job isolation or G-006 qualification.

## Independent provider transports

Issues #298 and #299 have no dependency on each other's source files. Separate GPT-6.1 Sol medium implementation threads own the GitHub runner and OCI registry packages. The coordinator owns shared documentation, issue records and one combined final affected check; no independent reviewer round is added. Each protocol has local HTTPS success/failure fixtures and focused Go tests/vet. Both remain unavailable to ordinary clients until the later server-owned declaration, authorization and execution path composes them.

The runner adapter follows the existing selected organization-group policy. It checks organization and repository identities, the exact group, `selected` repository visibility and bounded complete membership. A registration token is passed to a synchronous consumer through the existing short-lived credential value and then closed/wiped. Results retain only stage and expiry, including an attempted stage when the response or consumer fails. Exact owned runner cleanup refuses online or busy runners; the later controller must stop its one-job process before cleanup. No group configuration or repository permission is changed. Official [runner](https://docs.github.com/en/rest/actions/self-hosted-runners) and [runner-group](https://docs.github.com/en/rest/actions/self-hosted-runner-groups) API contracts were checked on 27-10-2026. Registration needs a separate purpose-specific organization runner credential; this does not authorize obtaining or activating one.

The registry adapter follows [OCI Distribution 1.1.1](https://github.com/opencontainers/distribution-spec/blob/v1.1.1/spec.md). It accepts an already scoped borrowed bearer credential, one OCI image manifest and reopenable config/layer streams. Descriptor sizes/digests are validated before any request. Existing blobs use exact HEAD checks; new blobs use monolithic upload; the manifest is committed only by digest and independently reread/hashed. Upload locations must stay at the configured HTTPS origin and current repository upload path. Provider authentication realms are not followed. It records attempted stages and never automatically retries an uncertain write. Streamed request bytes must still match after preflight before committing the manifest. Supported limits are one 1-MiB manifest, 128 blobs, 1 GiB per blob and 4 GiB total; bounded annotations are preserved in the exact hashed bytes; multi-platform indexes, external descriptors and tags remain unsupported in this bounded transport.

Both protocols require a caller-supplied current-authority/intent callback before requests and writes. An adapter callback does not itself establish a plan, durable intent, runner ownership or authorization. The later existing server/SQLite/plan engine must supply those checks. Provider GETs and mutations are not atomic, and uncertainty is never promoted to verified success. A publication receipt proves registry bytes; signing, provenance, build identity and runtime deployment remain separate checks.

## Controller-owned source enrollment and human procedure

Issue [#304](https://github.com/vegastack/vegastack-labs/issues/304) connects one protected exact source policy to the existing server-owned declaration, human-acknowledged plan, SQLite effect and scoped API/CLI. The stable policy omits a runner ID because no runner exists yet; actual assigned-job observations still require and compare the real runner ID. The protected binding distinguishes the provider repository owner from the responsible human. SQLite stores the complete private policy snapshot; public declarations, plans, records and audit expose opaque IDs and its digest.

Registration remains `registered` / `not-qualified`. It cannot launch a runner, admit a job, read a provider credential or deploy an image. A draft is inert, and the local registration row appears only after the exact current acknowledged plan applies. Current principal/device/author/execute/ack grants, state, epoch, lease and protected profile must remain valid at insertion and scoped reads. This adds no enrollment update/delete workflow; existing database recovery remains controlling.

For the matching human procedure:

1. An administrator configures finite protected `ciEnrollmentBindings` in the server profile and the existing exact author/read/execute/ack grants. This development implementation does not change a live profile or create grants. Obtain current state revision and recovery epoch through authorized reads, then prepare the bounded opaque draft request with its enrollment/binding IDs, idempotency key and reason digest.
2. Run `vsk-labs ci enrollment draft --config <operator-profile> --file <draft-request> --output json`. Review the returned inert declaration and binding digest.
3. Run existing `vsk-labs plan --config <operator-profile> --declaration-id <returned-id> --revision <returned-revision> --output json`. That command commits the declaration inertly and creates the bound plan; there is no separate new commit command.
4. Obtain the existing configured human-channel acknowledgement for that exact immutable plan, then run `vsk-labs apply --config <operator-profile> --plan-id <plan-id> --output json`.
5. Verify `vsk-labs ci enrollment show --config <operator-profile> --enrollment-id <enrollment-id> --output json` and `vsk-labs ci enrollment list --config <operator-profile> --output json` report the expected opaque binding digest and truthful registration/admission states. On drift or revoked authority, prepare a fresh eligible plan; never edit database rows or automatically retry an uncertain effect.

Isolated Linux proof exercises the actual SQLite/API/acknowledgement/plan/run path: success, state/epoch drift, revoked author/execute/ack/device, cancellation and lease revocation at the insertion boundary. It also checks inert drafts, scoped reads, private-policy redaction, restart/profile drift and replay denial. The guest's tmpfs temporary directory correctly failed the durable database filesystem prerequisite; final proof used its protected owned disk directory. Native proof is software evidence, not live source enrollment, runner or fleet qualification.
