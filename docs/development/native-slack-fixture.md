# Isolated native Slack transport fixture

`vsk-labs qualification fixture-peer` runs a temporary loopback TLS/WebSocket peer for the explicitly prepared disposable native guest. It is fixture transport, not a Slack service, human approval, live-workspace proof or workload admission. The existing production Slack HTTP transport, Socket Mode decoder, identity mapping, exact acknowledgement checks and database owner remain unchanged. The peer never opens SQLite or calls the acknowledgement service.

The coordinator prepares the named isolated guest before invoking this command. This document grants no infrastructure permission. Do not apply these steps to inventory hosts, shared runner hosts or a production service. The coordinator owns the process lifetime and removal of the exact guest-only changes.

The fixed directory `/run/vsk-labs-native` must be root-owned with mode `0700`; its files must be root-owned regular single-link files with mode `0600`:

| File | Purpose |
| --- | --- |
| `slack-fixture.json` | Generated `NativeSlackFixtureScope`; exact guest serial, SSH identity, setup machine identity, compiled source, measured executable, Slack test mapping, setup bindings and original expiry |
| `server.crt`, `server.key` | Private fixture TLS certificate/key; certificate covers `slack.com` and `wss-native.slack.com` and outlives the bounded scope |
| `app-token`, `bot-token` | Synthetic fixture credentials only; use the closed fixture prefixes required by the implementation, never real Slack credentials. No trailing newline; matching digest in scope. |
| `approvals.json` | Generated `NativeSlackFixtureApprovalList`, at most 48 exact prepared plan bindings; loaded again for each published plan |

The scope's `issuedAt` and `expiresAt` define one original window of at most four hours. Restarting the peer cannot extend that window. The peer independently checks the actual SMBIOS serial, SSH public key, machine ID, running executable and compiled source revision. It listens only on `127.0.0.1:443`. Only the existing `/api/apps.connections.open`, `/api/chat.postMessage` and `/link/` wire paths exist. WebSocket tickets are random, short-lived and single-use. Each allowed plan is consumed once per peer process, and at most 64 cards can be selected during that process.

Before initial setup, prepare the real generated `LocalSetupRequest` at `/etc/vsk-labs/control/setup.json`, owned by its nonroot service UID with mode `0600`. Its original byte digest, setup ID and machine identity must match the scope. `setupPlanDigest` is the exact canonical review digest produced by the existing local setup review construction, including the sanitized request and exact Slack mapping. It is not the request-file digest. Initial setup selection additionally requires state revision and recovery epoch zero, the exact setup expiry, and the existing initialization reason digest. Setup still runs through `vsk-labs server run --setup`, its release/profile checks, real Slack adapter and existing approval persistence.

For ordinary prepared plans, add only the exact plan ID/digest, target/reason digests, state revision, recovery epoch, expiry and `approve` or `reject` selection to the protected allowlist. No wildcard or fallback is supported. Plan expiry cannot exceed the fixture deadline. The peer copies the production adapter's per-request nonce into its Socket Mode envelope; it never creates a database approval directly. Unknown, changed, expired, duplicated or previously consumed plan bindings are refused.

The coordinator must install the private test CA trust and map only `slack.com` and `wss-native.slack.com` to `127.0.0.1` inside this guest. Never disable TLS verification or redirect real Slack tokens to this peer. Deliver the same synthetic token bytes through the existing native credential path to the ordinary server. The peer is a separate temporary invocation of the same executable, not another database writer or a persistent service. Start it before setup and retain it only for the approved test window, including any service handoff. Stop it and remove the exact guest trust/name-resolution changes during teardown. A TLS startup failure, missing allowlist or uncertain cleanup is a failed/pending fixture condition, never qualification evidence.

The focused wire test uses the actual production HTTP transport, TLS validation, WebSocket connection and Slack adapter decoder with synthetic credentials and an isolated test listener. It proves software composition only. Actual pre-database setup, native credential delivery, service handoff and native recovery remain separate required scenarios.

For the setup scenario, the protected manifest sets `runControlSetup` and the exact nonroot `controlServiceUid`/`controlServiceGid`. Preparation supplies `/etc/vsk-labs/control/setup.json`, `/etc/vsk-labs/control/server.json`, and the service-owned mode0700 credential directory `/run/vsk-labs-control-credentials`; the latter uses the same synthetic Slack material through the ordinary credential resolver. The peer launches only the measured `/usr/local/bin/vsk-labs` with fixed argument arrays. Its child is the ordinary foreground server and sole SQLite writer. The peer keeps a process handle and bounded private output, owns shutdown, and never creates a unit or detached child.

Before publishing `/run/vsk-labs-native/control-setup-observation.json`, the parent measures incomplete-file refusal, fresh setup through actual Slack transport, populated-database refusal, a competing ordinary writer refusal, graceful restart, and crash/restart. Refusals require identical file identities and byte digests for the database, sidecars and approval receipt. It removes only its own unchanged incomplete fixture; unexpected contents remain for diagnosis. Restart health comes from the existing same-UID authenticated control-health helper, retaining the same instance and epoch. The observation also binds the protected setup approval receipt and live parent identity. A later producer is joined to the actual initialization intent and canonical audit chain by the server; no pre-database run is invented.

The final foreground child remains supervised for the ordinary role handoff. After the predecessor exits, the peer waits for the real protected completed handoff receipt and current service health, then continues serving exact allowlisted approvals until its original expiry. Qualification keeps setup observations separate from current-epoch role evidence; an old setup observation crosses a recovery epoch only through the actual verified restore binding. These source paths and predicate tests are not evidence that a native setup scenario has run.
