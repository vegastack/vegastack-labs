# Native credential authority (development fixture)

This profile is dormant until #140's exact mapping, #143's real disposable-systemd acceptance, and #141's lifecycle verifier are independently reviewed and integrated. It grants no inventory-host installation or gate activation.

The unprivileged `vsk-labs server run` account is `vsk-labs`. The Ansible role under `ansible/roles/native_credential_authority` accepts an explicit sorted `.service` list, the local 32-character machine ID, and exact sorted probe tuples (`unit_name`, `credential_name`, non-root `uid`, non-root `gid`). The tuples must be derived from the #140 sealed positive and denied reader map. The role requires `/usr/local/bin/vsk-labs` to be a root-owned regular executable with no group/world write bit, then installs one root-owned polkit rule for `manage-units`/`restart` on enrolled units, two fixed-argument sudoers entries for the same binary's read-only policy check and metadata-only probe modes, and one root-owned policy readable by the `vsk-labs` group. It explicitly denies other `manage-units` tuples, `manage-unit-files` and daemon reload for the service account so later permissive polkit rules cannot widen this grant. The policy check is a one-shot root process because polkit rejects non-root callers that pass action details. It verifies the caller PID/start ticks/UID against live `/proc` and sudo's authenticated UID before and after its checks; the unprivileged caller also requires the effective C-locale `sudo -n -l` aggregate to contain exactly those two commands. Unknown policy output or any extra grant blocks operation.

Before any disposable-host application, confirm Debian 13/systemd, polkitd, sudo, util-linux `nsenter`, Ansible and a separate approved exact fixture plan. Prepare two synthetic non-root service accounts plus `vsk-labs`; install a root-owned development build of the single binary at `/usr/local/bin/vsk-labs`. Prepare `vsk-native-allow.service` with `LoadCredential=credential-a:<synthetic-fixture-file>`, `User=vsk-native-positive`, and a long-running process, plus a distinct `vsk-native-other.service`. No real material belongs in the fixture. Apply the role using its explicit inputs. Check the rendered JavaScript syntax (`node --check < /etc/polkit-1/rules.d/00-vsk-native-credential-restart.rules` on the fixture), sudoers syntax (`visudo -c -f ...`), exact file ownership/modes, and polkitd startup/logs before running the matrix. The [Debian polkitd manual](https://manpages.debian.org/trixie/polkitd/polkitd.8.en.html) confirms the daemon drops to the `polkitd` user; the [util-linux `nsenter` manual](https://kernel.googlesource.com/pub/scm/utils/util-linux/util-linux/%2B/refs/tags/v2.41.1/sys-utils/nsenter.1.adoc) documents the mount namespace path and `--setgid` group clearing.

On that disposable fixture only, create a root-owned mode `0600` `/run/vsk-native-authority-disposable` marker and run `VSK_NATIVE_AUTHORITY_DISPOSABLE=1 bash tooling/native-credential-authority-acceptance.sh`. The script checks allowed restart; rejected different unit, verbs, unit-file and transient operations; positive and denied direct-open outcomes under exact UIDs/GIDs; malformed/extra-argument rejection; and output canaries. It must also demonstrate that an earlier permissive polkit rule and a broad sudoers rule disqualify the authority, while a later permissive polkit rule cannot override the explicit denial. Recheck the service process identity, namespace and credential inode before accepting a result. Record fixture image/systemd/polkit/sudo/nsenter versions, exact commit and sanitized test result in #143 evidence. A Docker PID1 systemd fixture used during development did not expose its `LoadCredential` directory to the service process; a manually created path exercises probe mechanics but does not count as native credential acceptance. A real disposable VM or equivalent host must pass the whole matrix. Fixture-only success never closes G-007.

The manual `ci.yml` dispatch accepts `native_credential_sha` only on the fixed `feat/143-native-credential-authority` branch. The job checks that input against both `GITHUB_SHA` and the clean checkout, permits only disposable `vsk-node-01` or `vsk-node-06`, then uses `tooling/native-credential-authority-ci-fixture.sh` to install only synthetic users, two synthetic units and exact role files. It refuses pre-existing accounts, UIDs/GIDs, units or paths. A root-owned run marker binds cleanup to the exact workflow run and SHA; both EXIT/TERM traps and an unconditional workflow cleanup step remove the fixture. The runner must have Ansible installed; the workflow does not install host packages. If the runner lacks non-interactive sudo, Ansible, systemd, polkit or another prerequisite, report the failed preflight as a blocker and do not use an inventory host as a substitute.

For removal or recovery on the disposable fixture, stop verifier use, remove the exact three role-owned files, verify restart and probe are both denied, then reapply the same reviewed role inputs and rerun the matrix. Do not remove a policy from an inventory host through this development procedure. A changed machine ID, executable inode or ownership, unit enrollment, reader tuple, target process, namespace or credential inode blocks verification until a new approved plan and role application requalify it.
